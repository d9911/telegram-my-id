# Работа Telegram My ID после закрытия окна

В **Настройки → Закрытие окна** включите **Продолжать работу бота после закрытия приложения**.
Переключатель сохраняется автоматически, отдельно от путей подключения. После этого
запустите бота своей кнопкой. Закрытие окна завершает GUI, а отдельный worker продолжает
обрабатывать Telegram API. Повторное открытие приложения подключается к нему; второй
worker не создаётся. Кнопка **Остановить бота** останавливает именно этот процесс.

При выключенном переключателе закрытие окна запрашивает остановку, дожидается завершения
worker и закрывает GUI. По умолчанию переключатель выключен, чтобы сохранить прежнее
поведение. Открытие приложения само по себе не запускает нового бота.

Работа в фоне предполагает включённый компьютер, работающую сеть и отсутствие сна.
Автозапуск при входе, системная служба и автоматический запуск после перезагрузки
не устанавливаются. Токен должен быть действительным; настоящий API требует подключения.

## Управление без окна

В установленном приложении headless-бинарник поддерживает локальные команды:

```sh
# macOS, если приложение установлено в Applications:
"/Applications/TelegramMyID.app/Contents/MacOS/telegram-bot" --background-status
"/Applications/TelegramMyID.app/Contents/MacOS/telegram-bot" --stop-background

# Ubuntu:
telegram-bot --background-status
telegram-bot --stop-background
```

Windows: запустите `telegram-bot.exe --background-status` или
`telegram-bot.exe --stop-background` из каталога установленного приложения.
Эти команды не требуют токена и не отправляют запросы Telegram: они управляют
авторизованным локальным worker текущего пользователя.

Перед обновлением, удалением или пересборкой работающей release-копии **остановите бота**,
затем закройте окно. Одного закрытия окна при включённом фоне недостаточно.
Установочные блокировки удерживаются также worker-процессом.

## Настройки и секреты

- `settings.json` и выбранный `data_dir` сохранены без изменения формата.
- Новый `background-behavior.json` в каталоге приложения хранит только булеву настройку.
- Worker запускается из того же установленного GUI-executable, с отдельной сессией
  на Unix и отдельной группой без консоли на Windows. Python, Cargo и checkout не нужны.
- Токен и proxy передаются через анонимный stdin-канал, не через аргументы или новый
  конфигурационный файл. Введённый вручную токен остаётся в памяти worker до его остановки,
  даже если GUI закрыт. Существующий выбранный `.env` не изменяется.
- Управление слушает только loopback на выбранном ОС порту и требует случайную capability.
  `background/worker.json` содержит только PID, порт и capability; на Unix каталог имеет
  режим 0700, файл — 0600. На Windows используется пользовательский профиль и его ACL.
- Общая файловая блокировка исключает повторный worker. Процессы по порту или произвольному
  PID не завершаются. Прежняя блокировка каталога данных продолжает защищать languages.json.
- Журнал содержит ограниченный буфер очищенных событий в памяти; Telegram-токен в него
  не записывается. После завершения worker файл активного управления удаляется.

Источники реализации: `src/background.rs`, `src/desktop/controller.rs`,
`src/desktop/mod.rs`, `src/main.rs`, `src/bin/telegram-bot.rs`.

## Проверка 26 октября 2026

- macOS arm64: fmt, строгий Clippy, все 17 существующих тестов; новых тестов в репозитории нет.
- Проверена реальная копия из DMG вне checkout с отдельным HOME: переключатель доступен,
  сохраняется и восстанавливается после повторного открытия. Проверены оба режима через ⌘Q.
- С включённым фоном GUI-процесс завершился, worker остался доступен в фазе Connecting;
  затем он остановился по авторизованной команде. Соединение направлялось в локальный
  имитатор proxy; успешное подключение к настоящему Telegram на Mac не проверялось.
- С выключенным фоном реальное macOS-окно завершилось вместе с worker.
- Ubuntu 24.04 arm64: реальный runtime отправлял getMe/getUpdates локальному HTTPS API
  после завершения процесса с production-контроллером. Проверены повторное подключение,
  сохранение флага, отказ повторного запуска, отказ stop с неверной capability,
  авторизованная остановка и режим остановки вместе с GUI-контроллером.
- HTTPS-проверка использовала отдельный проверочный CA только в окружении QA-процесса;
  системное доверие и проверки сертификата не отключались. Настоящие Telegram-сообщения,
  пользовательские токены и пользовательская база не использовались.
- Windows, Intel macOS и Ubuntu amd64 требуют нативной проверки; это не подтверждение
  работы этих платформ по результату сборки на arm64.
