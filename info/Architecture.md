## 🎯 Обзор архитектуры

Проект использует **Clean Architecture (Hexagonal Architecture)** для обеспечения:
- ✅ Разделения ответственности (Separation of Concerns)
- ✅ Независимости бизнес-логики от фреймворков
- ✅ Легкого тестирования
- ✅ Масштабируемости
- ✅ Поддерживаемости кода

### Версии архитектуры

- **v1-v3**: Монолитная структура (legacy, сохранена в `db/` для обратной совместимости)
- **v4+**: Clean Architecture с разделением на слои

## 🧩 Принципы Clean Architecture

```
┌─────────────────────────────────────────────────────────┐
│                    Presentation Layer                    │
│              (Telegram API, Handlers)                     │
└──────────────────────┬────────────────────────────────────┘
                       │
┌──────────────────────▼────────────────────────────────────┐
│                  Application Layer                         │
│              (Use Cases, Handlers)                        │
└──────────────────────┬────────────────────────────────────┘
                       │
┌──────────────────────▼────────────────────────────────────┐
│                    Domain Layer                           │
│         (Entities, Services, Repository Traits)           │
└──────────────────────┬────────────────────────────────────┘
                       │
┌──────────────────────▼────────────────────────────────────┐
│                Infrastructure Layer                       │
│    (Telegram Client, File System, Config, Persistence)    │
└───────────────────────────────────────────────────────────┘
```

**Правило зависимостей**: Внешние слои зависят от внутренних, но не наоборот!

## 📖 Описание слоёв

### 🎯 Domain Layer (Доменный слой)

**Назначение**: Содержит чистую бизнес-логику, независимую от внешних фреймворков.

#### `entities/` - Бизнес-сущности
- **`command.rs`**: Enum всех команд бота (`Start`, `InfoUser`, `RandomNumber`, etc.)
- **`user.rs`**: Доменная модель пользователя (пока placeholder для будущего расширения)

#### `repositories/` - Интерфейсы репозиториев
- **`language_repository.rs`**: Trait для работы с языковыми настройками пользователей
  - `get_language(user_id)` - получить язык пользователя
  - `save_language(user_id, lang)` - сохранить язык пользователя
  - `get_all_languages()` - получить все сохранённые языки

#### `services/` - Бизнес-сервисы
- **`locale_service.rs`**: 
  - Определение языка пользователя по его языковому коду
  - Получение объекта локализации (`Locale`)
- **`random_service.rs`**: 
  - Генерация случайного числа в диапазоне
  - Случайный выбор элемента из списка
- **`user_service.rs`**: 
  - Форматирование информации о пользователе для отображения

**Важно**: Domain Layer **НЕ ЗАВИСИТ** от других слоёв!

---

### 📱 Application Layer (Слой приложения)

**Назначение**: Оркестрация бизнес-сценариев (Use Cases) и обработка событий.

#### `handlers/` - Обработчики событий
- **`command_handler.rs`**: 
  - Обрабатывает команды (`/start`, `/info_user`, `/random_number`, etc.)
  - Маршрутизирует команды к соответствующим Use Cases
- **`message_handler.rs`**: 
  - Обрабатывает обычные текстовые сообщения
  - Используется для многошаговых команд (например, ввод диапазона для `/random_number`)
- **`callback_handler.rs`**: 
  - Обрабатывает нажатия на inline-кнопки (callback queries)
  - Используется для выбора языка

#### `use_cases/` - Бизнес-сценарии
- **`start_use_case.rs`**: 
  - Приветствие пользователя
  - Определение языка пользователя
  - Показ клавиатуры выбора языка
- **`info_user_use_case.rs`**: 
  - Получение информации о пользователе
  - Форматирование и отправка ответа
- **`random_number_use_case.rs`**: 
  - Запрос диапазона у пользователя
  - Генерация и отправка случайного числа
- **`random_choice_use_case.rs`**: 
  - Запрос списка значений у пользователя
  - Случайный выбор и отправка результата
- **`test_use_case.rs`**: 
  - Тестовая команда с демонстрацией функциональности
- **`language_use_case.rs`**: 
  - Сохранение выбранного языка пользователя
  - Подтверждение смены языка

**Зависимости**: Application Layer зависит от Domain Layer и Infrastructure Layer.

---

### 🔌 Infrastructure Layer (Инфраструктурный слой)

**Назначение**: Реализация внешних зависимостей (API, БД, конфигурация).

#### `telegram/` - Telegram API адаптер
- **`bot_client.rs`**: 
  - Обёртка над `teloxide::Bot`
  - Проверка подключения к Telegram API
  - Удобные методы для работы с ботом
- **`keyboard.rs`**: 
  - Создание inline-клавиатур для выбора языка
  - Утилиты для работы с кнопками

#### `persistence/` - Хранение данных
- **`language_repository_impl.rs`**: 
  - Реализация `LanguageRepository` trait
  - Сохранение языков в JSON-файл (`src/db/data/languages.json`)
  - Загрузка языков при старте приложения

#### `config/` - Конфигурация
- **`mod.rs`**: 
  - Загрузка переменных окружения из `.env` файла
  - Инициализация конфигурации при старте

**Зависимости**: Infrastructure Layer зависит от Domain Layer (реализует его интерфейсы).

---

### 🎨 Presentation Layer (Слой представления)

**Назначение**: Настройка UI и роутинга (пока минимально используется).

- **`dispatcher.rs`**: 
  - Настройка `teloxide` dispatcher (пока логика в `main.rs`)
  - В будущем может содержать конфигурацию роутинга

**Примечание**: В текущей реализации большая часть логики dispatcher находится в `main.rs`.

---

### 🔗 Shared Layer (Общий слой)

**Назначение**: Общие типы и утилиты, используемые во всех слоях.

- **`types.rs`**: 
  - `HandlerResult` - тип результата обработчиков
  - `UserLanguages` - тип для хранения языков пользователей
  - `WaitingForRange`, `WaitingForChoice` - типы для состояния пользователя
- **`errors.rs`**: 
  - Кастомные типы ошибок приложения

---

### 🌍 Locales (Локализация)

**Назначение**: Независимый модуль для многоязычности.

- **`mod.rs`**: 
  - Центральный модуль с функцией `get_locale(lang_code)`
  - Определение языка по коду (ru, en, es, ko)
- **`{ru,en,es,ko}.rs`**: 
  - Файлы с переводами для каждого языка
  - Хранят `HashMap<String, &'static str>` с ключами переводов

**Поддерживаемые языки**:
- 🇷🇺 Русский (ru)
- 🇬🇧 Английский (en)
- 🇪🇸 Испанский (es)
- 🇰🇷 Корейский (ko)

## 🔄 Поток данных

### Пример: Обработка команды `/info_user`

```
1. Telegram API
   └─> Получение сообщения с командой /info_user
       │
2. Presentation Layer (main.rs)
   └─> Dispatcher маршрутизирует команду
       │
3. Application Layer
   └─> CommandHandler::handle()
       └─> InfoUserUseCase::execute()
           │
4. Domain Layer
   ├─> UserService::format_user_info()  (форматирование)
   └─> LocaleService::get_locale()      (получение языка)
       │
5. Infrastructure Layer
   └─> BotClient::send_message()        (отправка в Telegram)
       │
6. Telegram API
   └─> Пользователь получает ответ
```

### Пример: Выбор языка пользователем

```
1. Пользователь нажимает кнопку "🇷🇺 Русский"
   │
2. CallbackHandler::handle()
   └─> LanguageUseCase::execute()
       │
3. Domain Layer
   └─> LanguageRepository::save_language()
       │
4. Infrastructure Layer
   └─> FileLanguageRepository::save_language()
       └─> Запись в languages.json
       │
5. Ответ пользователю: "Язык изменён на русский"
```

## 🔧 Конфигурация

### Переменные окружения

Создайте файл `.env` в корне проекта:

```env
TELOXIDE_TOKEN=your_bot_token_here
```

**Важно**: 
- Файл `.env` должен быть в `.gitignore`
- Используйте `.env.copy` как шаблон (если есть)

### Инициализация

При запуске приложения:
1. Загружаются переменные окружения из `.env` (через `infrastructure::config`)
2. Инициализируется логгер (`pretty_env_logger`)
3. Создаётся `BotClient` и проверяется подключение к Telegram API
4. Загружаются сохранённые языки пользователей из `src/db/data/languages.json`
5. Настраивается dispatcher и запускается бот

## 🎓 Преимущества архитектуры

### ✅ Разделение ответственности
Каждый слой имеет чёткую ответственность:
- **Domain**: Бизнес-логика
- **Application**: Оркестрация сценариев
- **Infrastructure**: Внешние зависимости
- **Presentation**: UI логика

### ✅ Независимость от фреймворков
Бизнес-логика не зависит от `teloxide` или других библиотек. Можно легко заменить Telegram на другой мессенджер.

### ✅ Тестируемость
Каждый слой можно тестировать независимо:
- Domain Layer: Unit-тесты без моков
- Application Layer: Интеграционные тесты с моками Infrastructure
- Infrastructure Layer: Тесты с реальными адаптерами

### ✅ Масштабируемость
Легко добавлять новые функции:
1. Добавить команду в `domain/entities/command.rs`
2. Создать Use Case в `application/use_cases/`
3. Добавить обработку в `application/handlers/`

### ✅ Поддерживаемость
Код организован логически, легко найти нужный модуль и понять его назначение.

## 📝 Примечания

- **Legacy модуль `db/`**: Сохранён для обратной совместимости, но новая архитектура использует `infrastructure/persistence/`
- **Dependency Injection**: Все зависимости передаются через конструкторы (явная DI)
- **Arc для shared state**: Используется `Arc` для разделения состояния между обработчиками
- **Async/Await**: Вся работа с Telegram API асинхронная (через `tokio`)
